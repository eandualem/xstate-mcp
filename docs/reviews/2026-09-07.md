## Assessment

The project has a useful, focused purpose and a small architecture worth keeping.
An agent can use machine state as evidence while building a frontend, then verify
the result through the UI. The handler separation, stderr logger, structured tool
results, per-actor ring buffers, origin restrictions, and existing regression
tests are useful foundations.

The current release is not ready for a reliable clean-clone demonstration.
Green unit tests mask failures at the application-to-WebSocket and MCP lifecycle
boundaries. Fix these contracts before adding more tools. The review adds shared
instructions and documentation; runtime fixes remain separate GitHub issues.

## Reproduced failures

### P1 — real Stately messages register no actors

Five messages from a real machine produced zero actor records. Each message
contains `id: null`, rejected by the optional-string schemas in
[src/types.ts](../../src/types.ts). The first error is
`Expected string, received null` at `id`. Epoch-millisecond timestamp strings
also need normalization to the documented timestamp format.
[#1: Accept real Stately inspection messages and normalize timestamps](https://github.com/eandualem/xstate-mcp/issues/1)

### P1 — the minimal adapter loses startup registration

Running the README's `new WebSocket(...)` followed immediately by actor creation
drops all three startup inspection messages because the socket is still
CONNECTING. Starting after OPEN registers the actor, but native JSON serialization
omits definition and parent metadata. The bidirectional example also depends on
an unimplemented lookup helper and must use the socket owning the actor.
A complete adapter is the highest-value capability to add.
[#13: Ship a complete development adapter for startup, reconnect, and event dispatch](https://github.com/eandualem/xstate-mcp/issues/13)

### P1 — a valid JSON null frame crashes the entire CLI

A connected peer sending the text `null` causes exit code 1 at `obj.type` in
[src/ws-server.ts](../../src/ws-server.ts), before schema validation. Control
responses also bypass validation through type assertions.
[#2: Validate WebSocket envelopes before dispatch so null cannot crash the server](https://github.com/eandualem/xstate-mcp/issues/2)

### P1 — two applications mix identity, state, and command ownership

Registering `x:0` from two sockets leaves one actor owned by the second. A
snapshot from the first then changes the second actor's state. Sending an
acknowledgement from the wrong socket also settles a request when that peer is
given the request ID. This demonstrates missing sender validation, not a method
for guessing random UUIDs. Introduce application identity and enforce ownership.
[#3: Namespace application sessions and enforce socket ownership](https://github.com/eandualem/xstate-mcp/issues/3)

### P1 — subscription promises and notification lifecycle are incomplete

The server advertises `resources: {listChanged: true}`; a real
`resources/subscribe` request fails with `-32601 Method not found`. Registration
before connecting MCP transport causes an unhandled `Not connected` rejection.
The fixed actor-list resource is not notified when its content changes.
[MCP specifies subscription capabilities and requests separately from list-change notifications](https://modelcontextprotocol.io/specification/2025-11-25/server/resources).
[#4: Make MCP resource subscriptions and notification lifecycle correct](https://github.com/eandualem/xstate-mcp/issues/4)

### P1 — library imports and CLI lifecycle have process side effects

Importing the advertised sandbox factory's module executes `main()`. With an
invalid port environment value, the import exits the caller with code 1. A busy
WebSocket port logs EADDRINUSE while MCP initialization still succeeds. Closing
stdin leaves the process listening; signal shutdown exits before asynchronous
cleanup is awaited. These are separate subprocess reproductions.
[#5: Separate importable server factories from CLI startup and cleanly manage shutdown](https://github.com/eandualem/xstate-mcp/issues/5)

### P2 — static event eligibility disagrees with XState

For `on: {'user.*': 'done'}`, XState's live `.can({type:'user.save'})` is true
and this tool returns false. With a root GO handler and child `on:{GO:{}}`,
XState returns false while the tool reports true. Missing definitions also
produce a definitive false instead of an unavailable answer. Keep guard
limitations explicit and correct event-selection semantics.
[#9: Make event eligibility reflect XState wildcard and forbidden-transition semantics](https://github.com/eandualem/xstate-mcp/issues/9)

### P2 — error and completion details are absent from agent snapshots

A record containing `status:'error'`, an error message, and output returns only
status through `get_actor_state`. The store discards error, while tools/resources
omit stored output. Source review also shows timeline detection ignores
status-only changes. Promise actors and failure recovery need this evidence.
[#10: Preserve actor errors, outputs, and status changes in debugging data](https://github.com/eandualem/xstate-mcp/issues/10)

## Maintenance and code-review improvements

- **Patch and triage dependencies.** The locked ws 8.19.0 is in the affected range
  for a receiving-path memory-exhaustion issue, fixed in 8.21.0.
  [Maintainer advisory](https://github.com/websockets/ws/security/advisories/GHSA-96hv-2xvq-fx4p).
  The Vitest advisory applies when its UI/API server listens; this review used
  `vitest run` and did not demonstrate that exposure.
  [Vitest advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-5xrq-8626-4rwp).
  Node 20 is EOL; choose a maintained LTS matrix and verify it.
  [Node release status](https://nodejs.org/en/about/previous-releases).
  [#6: Refresh audited dependencies and define a maintained Node.js support matrix](https://github.com/eandualem/xstate-mcp/issues/6)
- **Test contracts in CI.** Existing tests exercise valuable local behavior,
  but no dependency produces genuine XState messages in the suite. Add real
  producer fixtures, registered MCP-surface tests, packed-CLI subprocess checks,
  and test type checking. Automate the existing quality gate too.
  [#7: Run quality gates and real XState-to-MCP contract tests in CI](https://github.com/eandualem/xstate-mcp/issues/7)
- **Fix release provenance.** Checkout 1.0.1, npm 1.0.3, and MCP/registry metadata
  1.0.0 drift. Bundles match, so avoid assuming unpublished runtime changes.
  Use one version source and validate release/registry metadata from a known commit.
  [#8: Reconcile published versions and make releases reproducible](https://github.com/eandualem/xstate-mcp/issues/8)
- **Validate inputs and bound resources.** Per-actor entry counts do not bound
  the total actor count, snapshot/definition bytes, or pending requests. Numeric
  tool inputs lack integral/range constraints; configuration uses permissive
  parseInt. Add explicit retention, overflow reporting, and shared output budgets.
  [#11: Bound retained data and validate numeric limits for long debugging sessions](https://github.com/eandualem/xstate-mcp/issues/11)

Keep refactoring proportional. Useful future cleanup includes shared snapshot
projection across tools/resources/prompts, listener disposal, typed control
envelopes, and consistent errors. The serializer labels repeated shared objects
as circular, its declared string result can be undefined, and cyclic parent
metadata can disappear from the tree. These are source-review edge cases;
address them within serialization/validation work if supported inputs require it,
rather than creating a broad rewrite. Measure actor-list scans before optimizing.

## Capability roadmap

- **Connection diagnostics:** distinguish no browser, a connected but empty app,
  rejected frames, stale connections, and unsupported write commands. Negotiate
  protocol/adapter capabilities and expose application identity.
  [#14: Expose connection health and negotiated application capabilities](https://github.com/eandualem/xstate-mcp/issues/14)
- **Write policy and redaction:** provide read-only mode and actor/event controls,
  conservative command annotations, and consistent filtering across every data
  surface. Arbitrary send_event commands may trigger application side effects;
  acknowledgement does not prove a transition.
  [#15: Add explicit write controls and consistent inspection-data redaction](https://github.com/eandualem/xstate-mcp/issues/15)
- **Bounded verification:** wait for state/status or an event after a baseline,
  with timeout, cancellation, and disconnect semantics.
  [#12: Add bounded wait_for_state and wait_for_event verification tools](https://github.com/eandualem/xstate-mcp/issues/12)
- **Cross-actor diagnostics:** correlate a bounded application/subtree trace,
  state/context changes, and opt-in sanitized export. Mark inferred causality
  and keep event replay as a separate future decision.
  [#16: Add cross-actor traces and sanitized diagnostic export](https://github.com/eandualem/xstate-mcp/issues/16)

## Implementation order and demo gates

1. **Reliable operation:** fix malformed input and real inspection compatibility;
   isolate clients, deliver the adapter, correct subscriptions/process lifecycle,
   patch dependencies, and establish the actual integration gate.
2. **Useful agent feedback:** correct event eligibility and error/output visibility;
   add health/capabilities, wait operations, bounded data handling, and write/data
   controls. Reconcile release metadata before publishing.
3. **Small deterministic frontend example:** prove observe → act → verify using
   both MCP and browser assertions, including error/retry, refresh, and two tabs.
   [#17: Add a runnable frontend example that proves the complete MCP loop](https://github.com/eandualem/xstate-mcp/issues/17)
4. **Design Studio frontend-development demonstration:** let its coding agent
   implement a scoped feature with recorded runtime evidence and tests.
   [#18: Demonstrate Design Studio's coding agent developing its frontend with xstate-mcp](https://github.com/eandualem/xstate-mcp/issues/18)
5. **Optional richer traces:** cross-actor analysis/export can follow the first
   successful demo; it is not necessary to delay the basic proof for it.

[The demo plan](../demo-plan.md) defines the story and acceptance gates. Design
Studio currently has the right XState hierarchy but no inspection hook. Its
in-app assistant edits design documents; the external coding agent is the one
that will develop the frontend. The exact frontend feature should be selected
after confirming it is useful and absent in that repository.
